## 1. 标签系统的局限性

一个简单的 `[可破坏]`, `[可燃烧]` 标签过于笼统和“布尔化”（非0即1），它无法承载“过程”和“程度”的概念, 在高质量的游戏设计中，交互很少是瞬时的，而是有过程的

## 2. 解决办法

将描述性的**布尔标签**（例如 `[可破坏]`）升级为**量化属性**（例如 `{耐久度: 100/100}`）

- **旧模型（过于简单）**: 物体A有 `[可燃]` 标签，火焰B接触物体A，物体A着火
- **新模型（更精细）**: 物体A有 `{当前温度: 25, 燃点: 500, 耐久度: 100}` 属性, 火焰B持续对A施加影响，每秒提升其`当前温度`, 当`当前温度 >= 燃点`时，A的状态变为“燃烧”, 燃烧状态每秒对其`耐久度`造成伤害

### 2.1. 定义核心量化属性 Components

一个游戏实体（无论是生物、武器还是一个木箱）都是由多个组件构成的

**`HealthComponent` (生命/耐久度组件)**

- `currentHP`: 当前生命值/耐久度
- `maxHP`: 最大生命值/耐久度
- *适用对象*: 所有可以被“伤害”或“破坏”的物体，包括生物、门、宝箱、墙壁等

**`AttackComponent` (攻击组件)**

- `baseDamage`: 基础伤害值 (一个数值)
- `damageType`: 伤害类型 (一个或多个标签/枚举)
- *适用对象*: 所有能造成伤害的实体，如武器、法术、爆炸、陷阱等

**`ResistanceComponent` (抗性组件)**

- `resistances`: 一个**字典/映射表 (Dictionary/Map)**，这是设计的关键
  - `Key`: `damageType` (伤害类型)
  - `Value`: `multiplier` (伤害乘数)
- `armor`: 扁平减伤值 (可选，用于模拟护甲)
- *适用对象*: 所有可以被伤害的实体

### 2.2. 第二步：定义伤害类型 Damage Types

伤害类型是连接`AttackComponent`和`ResistanceComponent`的桥梁

伤害类型 (`DamageType`) 可以是一个枚举 (`Enum`) 或字符串标签:

- `Slashing` (砍击): 刀、剑、斧
- `Piercing` (穿刺): 矛、箭、匕首
- `Blunt` (钝击/敲击): 锤子、棍棒、拳头
- `Fire` (火焰): 火球术、燃烧的地面
- `Frost` (冰霜): 冰箭
- `Electric` (闪电): 雷电术

### 2.3. 伤害计算流程 Damage System

**事件触发**: 玩家用“铁锤”攻击“橡木门”

**获取数据**:

- 系统获取攻击方（铁锤）的 `AttackComponent`
  - `{ baseDamage: 20, damageType: 'Blunt' }`
- 系统获取被攻击方（橡木门）的 `HealthComponent` 和 `ResistanceComponent`
  - `{ currentHP: 150, maxHP: 150 }`
  - `{ resistances: { 'Slashing': 1.2, 'Piercing': 1.5, 'Blunt': 0.8, 'Fire': 2.0 }, armor: 5 }`

**查询抗性**:

- 系统在橡木门的 `ResistanceComponent` 中查找铁锤的 `damageType` (`'Blunt'`)
- 伤害乘数为 `0.8`, 这意味着橡木门对钝击有**抗性**，只会受到80%的伤害

**计算最终伤害**:

- `Final_Damage = (Attack.baseDamage * Resistance.multiplier) - Resistance.armor`
- `Final_Damage = (20 * 0.8) - 5`
- `Final_Damage = 16 - 5 = 11`

**应用伤害**:

- 橡木门的 `currentHP` 减去 `11`
- `newHP = 150 - 11 = 139`

**检查状态变更**:

- `currentHP` 是否小于等于 `0`？否, 橡木门依然存在, 如果HP归零, 则触发“被破坏”事件

### 2.4. 示例 刀 vs. 锤子 vs. 橡木门

**场景A：铁锤 攻击 橡木门**

- 锤子: `{ baseDamage: 20, damageType: 'Blunt' }`
- 木门抗性: `{ 'Blunt': 0.8 }` (对钝击有抗性)
- 伤害: `(20 * 0.8) - 5 = 11` (效果不佳)

**场景B：钢斧 (砍击) 攻击 橡木门**

- 斧子: `{ baseDamage: 18, damageType: 'Slashing' }`
- 木门抗性: `{ 'Slashing': 1.2 }` (对砍击**脆弱/弱势**)
- 伤害: `(18 * 1.2) - 5 = 16.6` (取整为17，效果更好)

**场景C：火箭 攻击 橡木门**

- 火箭: `{ baseDamage: 10, damageType: 'Fire' }`
- 木门抗性: `{ 'Fire': 2.0 }` (对火焰**极度脆弱**)
- 伤害: `(10 * 2.0) - 5 = 15` (虽然基础伤害低，但因为克制关系，效果显著)

## 3. 如何设计与拓展

**数据驱动设计 (Data-Driven Design)**: 整个系统的美妙之处在于它是数据驱动的

你不需要写新的代码来添加新武器或新材料

- **想添加一个“水晶傀儡”？** 只需创建一个新的实体模板，给它配置好`HealthComponent`和`ResistanceComponent`即可, 比如，它的抗性可能是 `{ 'Blunt': 2.0, 'Slashing': 0.5, 'Piercing': 0.3 }` (怕锤子，不怕刀剑)
- **想添加一把“灵能匕首”？** 只需创建一个新的武器，配置它的`AttackComponent`，伤害类型可以是新的 `'Psychic'`, 然后你需要更新现有物体的抗性表，告诉系统它们对`'Psychic'`的抗性是多少, 如果没定义，可以设置一个默认乘数（比如`1.0`）

**组合伤害类型**: 一个武器可以有多种伤害类型, 比如一把“霜火长剑”, 它的`damageType`可以是 `['Slashing', 'Fire', 'Frost']`, 计算伤害时可以分别计算，或者取最有效的一种

**与生物HP和防御力统一**: 这个系统可以完美地与生物的攻防系统统一

一个骑士的`ResistanceComponent`可能来自于他的盔甲, 提供高额的`armor`值和对`Slashing`的抗性, 而一个史莱姆的`ResistanceComponent`可能是天生的，对`Blunt`有抗性但对`Fire`脆弱

## 4. 燃烧 冰冻 状态

假如未来要有 使用火点燃干草垛 森林(不是干木的话 肯定燃点要高一些) 以及 房屋 等 这些 或者冬天 温度低 一些东西 可能会冻成冰块

### 4.1. `ThermalComponent`

这是继 `HealthComponent` 和 `ResistanceComponent` 之后, 我们需要的又一个核心组件, 它不关心直接的攻击, 只关心**温度**

`ThermalComponent` (热能组件) 包含以下属性:

- `currentTemperature`: `float` - 物体当前的温度, 这是动态变化的核心数值
- `ambientTemperature`: `float` - 物体所处环境的基准温度
- `thermalConductivity`: `float` - 导热系数 (0.0 - 1.0), 决定了物体向环境温度靠拢的速度, 以及从外部热源吸收/散失热量的速度, 金属的导热系数高, 木头、石头则较低
- `currentState`: `enum` - 物体当前的热能状态, 例如: `Normal` (常温), `Frozen` (冰冻), `Burning` (燃烧), `Melted` (熔化)
- 状态变迁阈值 (State Transition Thresholds)
  - `freezingPoint`: `float` - 冰点, 当 `currentTemperature` <= `freezingPoint` 时，可能触发 `Frozen` 状态
  - `ignitionPoint`: `float` - 燃点, 当 `currentTemperature` >= `ignitionPoint` 时，可能触发 `Burning` 状态
  - `boilingPoint`: `float` - 沸点, 当 `currentTemperature` >= `boilingPoint` 时，水会蒸发
  - `meltingPoint`: `float` - 熔点, 冰在高于此温度时会融化

### 4.2. 驱动系统 The Logic Systems

光有数据组件是不够的, 我们需要“系统”来处理逻辑, 这里至少需要两个关键系统

**`TemperatureUpdateSystem` (温度更新系统)** 

这个系统每一帧或每隔一小段时间运行一次, 它的唯一职责是更新所有拥有`ThermalComponent`的物体的`currentTemperature`

温度变化来源：

- 环境同化: `currentTemperature`会以`thermalConductivity`设定的速度, 缓慢地向`ambientTemperature`靠拢, 这就是冬天万物结冰, 夏天冰块融化的根本原因
  - `ΔT = (ambientTemperature - currentTemperature) * thermalConductivity * deltaTime`
- 外部热源/冷源:
  - 一个`Burning`状态的火堆会向周围释放热量, 范围内的物体会根据距离和火堆的热量强度, 持续增加`currentTemperature`
  - 一个“冰霜法术”击中物体, 会瞬间给其施加一个负向的温度变化
  - 两个物体接触时, 会根据导热系数和温差进行热量交换

**`StateChangeSystem` (状态变迁系统)** 

这个系统在`TemperatureUpdateSystem`之后运行, 它检查所有物体的`currentTemperature`是否越过了某个阈值, 并负责改变其`currentState`

工作流程:

- 检查燃点: `if (obj.currentTemperature >= obj.ignitionPoint && obj.currentState !== 'Burning')`
  - 条件：物体温度达到燃点，且当前没有在燃烧
  - 额外条件检查：是否接触氧气？是否是`[可燃]`材质？（这里可以和其他标签系统联动！）
  - 触发: 改变 `obj.currentState = 'Burning'`, 这个状态变更会产生一系列连锁效应 (Side Effects)
- 检查冰点: `if (obj.currentTemperature <= obj.freezingPoint && obj.currentState !== 'Frozen')`
  - 条件：物体温度达到冰点，且当前没有被冰冻
  - 额外条件检查：该物体是否含有水分？（例如，一个`[潮湿]`的标签）一块干燥的石头是不会“结冰”的，但一个潮湿的生物或一滩水会
  - 触发: 改变 `obj.currentState = 'Frozen'`

### 4.3. 连锁效应 (Side Effects) - 让世界活起来

状态的改变不仅仅是换个名字，它会动态地修改物体身上的其他组件，这正是涌现式玩法的魅力所在！

当`currentState`变为 `Burning` 时:

1. 添加/修改`AttackComponent`: 物体开始拥有一个持续的、范围性的火焰伤害光环, 接触它的生物会受到火焰伤害
2. 修改`HealthComponent`: 燃烧状态会持续对物体自身的`耐久度/HP`造成伤害
3. 添加`LightSourceComponent`: 成为一个光源, 照亮周围
4. 成为新的热源: 它自己也开始向外辐射热量，可能会点燃旁边的东西
5. 改变渲染模型: 视觉上出现火焰特效

当`currentState`变为 `Frozen` 时:

1. 修改`ResistanceComponent`: 物体的抗性发生变化, 例如, 冰块对“钝击(Blunt)”伤害变得极其脆弱 (`multiplier = 3.0`)，但对“穿刺(Piercing)”伤害有更高抗性 (`multiplier = 0.5`)
2. 添加`StatusEffectComponent`: 如果是生物, 会被施加“冰冻”状态, 无法移动和攻击 **(这就是简单的抽象, 到达冰点动物就变成冰, 融化了, 动物又活了)**
3. 成为新的冷源: 接触它的物体温度会下降 **(暂时没想到实现的办法)**
4. 改变物理属性: 地面结冰后会变得“湿滑”

### 4.4. 场景例子

场景A: 用火把点燃干草垛

1. 干草垛拥有`ThermalComponent`: `{ ignitionPoint: 150, thermalConductivity: 0.8 }` (燃点低，导热快)
2. 火把作为外部热源接触干草垛
3. `TemperatureUpdateSystem`迅速将干草垛的`currentTemperature`提升到150度以上
4. `StateChangeSystem`检测到越过燃点，将其`currentState`变为`Burning`
5. 干草垛开始燃烧，发光发热，并点燃旁边的其他干草垛，形成大火

场景B: 在森林里放火

1. 活的树木拥有`ThermalComponent`: `{ ignitionPoint: 400, thermalConductivity: 0.3 }` (燃点高，导热慢), 它可能还有一个`[潮湿]`的标签
2. 用同一个火把去点，`TemperatureUpdateSystem`提升其温度，但因为导热慢，需要持续烘烤一段时间才能达到燃点
3. 如果环境是雨天 (`ambientTemperature`低，且给物体附加`[潮湿]`标签)，点火会变得极其困难，因为环境会持续降低其温度

场景C: 冬天河水结冰

1. 水体拥有`ThermalComponent`: `{ freezingPoint: 0 }`
2. 游戏世界进入冬天，全局环境的`ambientTemperature`降至-10度
3. `TemperatureUpdateSystem`根据环境温度，缓慢降低水的`currentTemperature`
4. `StateChangeSystem`检测到水的温度低于0度，将其`currentState`变为`Frozen`
5. 连锁效应触发：水体从液体变为固体冰块，玩家可以在上面行走，但冰面很滑, 用重锤可以轻易砸开 **(怎么实现动态的东西呢 变了状态玩家就可以行走了)**

## 5. 为什么需要温度组件 - ECS 的概念

> 为什么不能把温度相关的东西直接放到 Resistance Component 中, 表示对火的抗性, 然后为火属性的物体增加火属性伤害呢?

在现代游戏引擎（尤其是使用实体组件系统 - ECS 架构）中, 一个核心的设计原则是关注点分离, 每个组件（Component）应该只负责一件事情，并且做得很好

- `ResistanceComponent` (抗性组件)：它的职责是定义一个物体“抵御”各种伤害类型的能力, 这是一个物体的*内在属性*或*装备属性*, 例如：火抗+50%，冰抗+20%，毒抗-10%。这些值通常在物体生成时确定，或者通过装备、Buff/Debuff 发生变化，但它们本身不代表物体正在受到的影响

- `TemperatureComponent` (温度组件)：它的职责是追踪一个物体当前的“热量状态”, 这是一个*动态变化的状态*, 例如：当前温度 85°C，燃烧点 100°C，冰冻点 0°C, 这个组件本身不关心伤害，只关心温度的变化

### 5.1. 将温度相关逻辑放入 `ResistanceComponent` (不推荐)

如果按照上面的想法，`ResistanceComponent` 可能会是这样：

```c++
struct ResistanceComponent {
    float fireResistance = 0.25f; // 25% 火焰抗性
    float iceResistance = 0.10f; // 10% 冰霜抗性
    // ... 其他抗性

    // 强行加入的温度相关状态
    float currentTemperature = 25.0f; // 当前温度
    float onFireThreshold = 500.0f; // 燃点
    float damagePerSecondFromFire = 10.0f; // 固定的火焰伤害值
};
```

优点 (Pros)

1. 初期简单直观: 对于一个只有“火焰”和“火焰伤害”的极简游戏, 把所有跟火相关的东西放一起，似乎很直接
2. 减少组件数量: 不需要额外的 `TemperatureComponent`, 对于刚开始构建系统的人来说, 感觉更“轻量”

缺点 (Cons):

- 这个组件现在做了两件完全不同的事：定义**属性**（抗性）和追踪**状态**（温度）, 这会导致组件功能混乱, 难以理解和维护 (Single Responsibility Principle)
- 极差的可扩展性 (Poor Scalability)
  - 如果加入“冰”呢？ 要怎么处理？`currentTemperature` 既要表示热, 也要表示冷, 当一个物体同时被火和冰攻击时, 这个单一的温度值如何结算？逻辑会变得非常复杂 **(下面会回答)**
  - 环境温度呢？ 比如一个角色走进沙漠, 体温会升高, 这个逻辑应该由谁处理？如果放在 `ResistanceComponent` 里, 难道 `EnvironmentSystem`要去修改一个抗性组件吗？这在逻辑上非常奇怪
  - 连锁反应呢？ 一个着火的木桶（温度很高）掉进水里，水应该被加热，木桶应该降温, 如果温度在 `ResistanceComponent` 里，物理系统（Physics System）需要去读写 `ResistanceComponent` 吗？这造成了不必要的耦合（Coupling）, 物理系统根本不应该关心“抗性”

### 5.2. 分离 `TemperatureComponent` 和 `ResistanceComponent` (推荐)

#### 5.2.1. 组件 (Components)

```c++
// 属性：定义如何抵抗伤害
struct ResistanceComponent {
    float fireResistance = 0.25f;
    float iceResistance = 0.10f;
    // ...
};

// 状态：追踪当前温度
struct TemperatureComponent {
    float currentTemperature = 25.0f;
    float heatSourceInfluence = 0.0f; // 周围热源强度
    float ambientTemperature = 25.0f; // 环境温度
    float burningPoint = 500.0f;      // 燃点
    float freezingPoint = 0.0f;       // 冰点
};

// 状态：追踪健康状况
struct HealthComponent {
    float currentHealth = 100.0f;
    float maxHealth = 100.0f;
};
```

#### 5.2.2. 系统 (Systems)

**`TemperatureSystem` (温度系统)**

1. 遍历所有带 `TemperatureComponent` 的实体
2. 根据周围环境（`ambientTemperature`）、接触的热源/冷源（`heatSourceInfluence`）来更新 `currentTemperature`, 例如，靠近火把，`heatSourceInfluence` 增加，`currentTemperature` 随之升高
3. 这个系统不关心伤害, 它只负责模拟温度变化

**`DamageSystem` (伤害系统):**

1. 遍历所有带 `TemperatureComponent` 和 `HealthComponent` 的实体
2. 检查 `TemperatureComponent`：如果 `currentTemperature` > `burningPoint`，则该物体处于“燃烧”状态
3. 如果要施加火焰伤害，它会查找实体是否还有 `ResistanceComponent`
4. 计算最终伤害：`finalDamage = baseFireDamage * (1 - resistance.fireResistance)`
5. 从 `HealthComponent` 的 `currentHealth` 中减去 `finalDamage`

**极佳的可扩展性和灵活性 (Excellent Scalability & Flexibility):** 这样设计就可以解决上面提到的问题

- 添加新机制: 想添加“冰冻”效果？只需在 `DamageSystem` 中增加一个逻辑：检查 `currentTemperature` < `freezingPoint`，然后施加“冰冻”状态或伤害, 无需改动 `TemperatureComponent` 的核心结构
- 添加环境效果: 创建一个 `EnvironmentSystem`，当玩家进入不同区域时，更新所有实体的 `TemperatureComponent` 中的 `ambientTemperature` 即可
- 实现连锁反应: 一个燃烧的物体碰到一个可燃物？`TemperatureSystem` 可以检测到它们的接触，并提高可燃物的 `currentTemperature`，最终可能点燃它, 一个热的物体掉进水里？`TemperatureSystem` 可以降低该物体的温度，同时提高水的温度, 这些复杂的交互变得清晰且可能

**促进涌现式玩法 (Emergent Gameplay):** 因为系统是基于物理状态（如温度）而不是写死的逻辑（如“被火烧到就掉血”），玩家可以创造性地利用这些系统, 例如在水里降温来抵御火焰伤害

> 回答上面提到的问题:
>
> 如果加入“冰”呢？ 要怎么处理？`currentTemperature` 既要表示热, 也要表示冷, 当一个物体同时被火和冰攻击时, 这个单一的温度值如何结算？逻辑会变得非常复杂
>
> 核心思想: 组件是数据容器, 系统是逻辑处理器
>
> - **`TemperatureComponent` (温度组件)**: 它本身**不包含任何逻辑**, 它只是一个数据表, 记录了物体的热力学状态`currentTemperature` 就是一个浮点数
>   - `> 100°C`: 燃烧
>   - `20°C`: 常温
>   - `< 0°C`: 结冰
> - **`TemperatureSystem` (温度系统)**: 这是一个活跃的处理器。在游戏的每一帧（或每个逻辑滴答），它会**主动地**去查找所有拥有 `TemperatureComponent` 的实体，并根据一套规则来更新 `currentTemperature` 的值。所有的复杂结算都在这个系统里进行
>
> 步骤 1: 收集所有温度影响源
>
> 在每一帧，`TemperatureSystem` 会检查一个实体受到了哪些温度影响, 这些影响不是直接修改 `currentTemperature`, 而是被视为待处理的**“温度变化请求”**
>
> 我们可以把这些“请求”也设计成临时的组件或事件
>
> - `HeatSourceComponent`: 代表一个持续的热源，比如一团篝火, 它有 `intensity` (强度) 和 `radius` (范围) 属性
> - `ColdSourceComponent`: 代表一个持续的冷源，比如一个冰霜陷阱
> - `ThermalShockEvent`: 代表一个瞬时的温度冲击事件, 比如：
>   - 一个火球术击中，产生一个 `ThermalShockEvent { change: +300 }`
>   - 一个冰锥术击中，产生一个 `ThermalShockEvent { change: -250 }`
>
> 步骤 2: 在 `TemperatureSystem` 中进行统一结算
>
> `TemperatureSystem` 的更新循环会执行以下逻辑：
>
> 1. 获取基础温度: 读取实体 `TemperatureComponent` 中的当前环境温度 `ambientTemperature`, 比如在雪地里是-10°C, 在沙漠里是40°C
> 2. 计算自然温度回归: 物体会自然地向环境温度靠拢, 这是一个平滑的变化过程,  `naturalChange = (ambientTemperature - currentTemperature) * normalizationFactor;`
>    - `normalizationFactor` 是一个很小的系数，代表物体保温/散热的能力
>    - 如果物体比环境热，`naturalChange` 是负数（降温）
>    - 如果物体比环境冷，`naturalChange` 是正数（升温）
> 3. 累加所有外部影响: 系统会查找所有作用于该实体的外部影响源 `externalChange = 0;`
>    - 被火球击中？`externalChange += 300;` (来自 `ThermalShockEvent`)
>    - 被冰锥击中？`externalChange -= 250;` (来自 `ThermalShockEvent`)
>    - 站在篝火旁？`externalChange += 20 * deltaTime;` (来自 `HeatSourceComponent`)
>    - 踩在冰霜陷阱上？`externalChange -= 15 * deltaTime;` (来自 `ColdSourceComponent`)
> 4. 计算最终净变化: `totalChange = naturalChange + externalChange;`
> 5. 更新最终温度: 将计算出的总变化应用到 `currentTemperature`,  `component.currentTemperature += totalChange * deltaTime;` (`deltaTime` 是自上一帧以来的时间, 确保变化与帧率无关)
>
> 一个角色同时被火球和冰锥击中
>
> 假设一个角色（当前温度 25°C，环境温度 25°C）在同一时刻被一个+300的火球和一个-250的冰锥击中
>
> `TemperatureSystem` 的结算过程如下：
>
> 1. `currentTemperature` = 25°C, `ambientTemperature` = 25°C
> 2. `naturalChange` = (25 - 25) * factor = 0 角色温度与环境一致，无自然变化
> 3. `externalChange` = (+300) + (-250) = +50 火球和冰锥的效果在这里被简单地**代数叠加**
> 4. `totalChange` = 0 + 50 = 50
> 5. `newTemperature` = 25 + 50 = 75°C
>
> 角色的温度从25°C上升到了75°C, 他感觉很热, 但还没有达到燃点, 如果只有火球, 他会变成325°C并开始燃烧, 如果只有冰锥, 他会变成-225°C并可能被深度冻结

> 所有的结算逻辑都集中在 TemperatureSystem 中, 当需要调整“冰火相遇”的效果时（比如你希望它们接触时能产生“爆炸”或“水蒸气”），你只需要修改 TemperatureSystem 的一处代码，而不需要去改动火球、冰锥、篝火、陷阱等所有相关事物的代码 
>
> 解释:
>
> 火球和冰锥本身没有任何“逻辑”，它们只是“数据”的载体
>
> 火球实体 = `移动组件` + `视觉特效组件` + `碰撞组件` + `瞬时温度改变请求{数值: +300}`
>
> 冰锥实体 = `移动组件` + `视觉特效组件` + `碰撞组件` + `瞬时温度改变请求{数值: -250}`
>
> 看到关键了吗？火球和冰锥的任务只是在击中目标时，给目标“贴”上一个“温度改变请求”的标签（数据）, 它们自己根本不知道这个请求意味着什么，任务就算完成了
>
> 真正的“大脑”是 `TemperatureSystem`, 它就像一个总管, 每一帧都在巡视整个游戏世界
>
> 场景一：初始版本（冰火仅互相抵消）
>
> `TemperatureSystem` 的工作流程（它的内部代码）可能是这样的
>
> ```c++
> void Update() {
>     // 1. 遍历游戏世界里每一个“实体”（entity）
>     for (each entity in world) {
>         // 2. 收集这个实体身上所有“温度改变请求”
>         float totalChange = 0;
>         for (each request on entity) {
>             totalChange += request.value; // e.g., +300 来自火球, -250 来自冰锥
>         }
> 
>         // 3. 如果有请求，就应用它
>         if (totalChange != 0) {
>             entity.temperatureComponent.currentTemperature += totalChange;
>         }
>         
>         // 4. 清理掉已经处理完的请求
>         entity.RemoveAllTemperatureRequests();
>     }
> }
> ```
>
> 在这个版本里，如果一个实体同时被冰火击中, `totalChange` 会是 `300 + (-250) = 50`, 系统只会给实体升温50度
>
> 场景二：升级版本（加入“蒸汽爆炸”效果）
>
> 现在, 我们想实现“冰火相遇产生蒸汽爆炸”的效果, 根据我们刚才的讨论, 我们**不需要去碰火球和冰锥的代码**, 它们的工作方式完全不变！
>
> 只需要修改 `TemperatureSystem` 这个总管的工作手册:
>
> ```c++
> // TemperatureSystem 的简化逻辑 - 版本 2 (升级版)
> void Update() {
>     for (each entity in world) {
>         // 2. 收集请求，但这次要分开收集
>         bool hasHeatRequest = false;
>         bool hasColdRequest = false;
>         float totalChange = 0;
> 
>         for (each request on entity) {
>             totalChange += request.value;
>             if (request.value > 0) hasHeatRequest = true;
>             if (request.value < 0) hasColdRequest = true;
>         }
> 
>         // 3. *** 在这里加入新的交互规则！***
>         if (hasHeatRequest && hasColdRequest) {
>             // 如果同时有加热和制冷的请求，就触发特殊效果！
>             CreateSteamExplosion(entity.position);
>             // 也许爆炸造成了伤害
>             entity.healthComponent.TakeDamage(20, "Steam");
>             // 因为能量已经通过爆炸释放了，所以不再改变温度
>             totalChange = 0; 
>         }
> 
>         // 4. 应用最终的温度变化
>         if (totalChange != 0) {
>             entity.temperatureComponent.currentTemperature += totalChange;
>         }
> 
>         // 5. 清理请求
>         entity.RemoveAllTemperatureRequests();
>     }
> }
> ```
>
> 这意味着什么？
>
> 1. **逻辑集中化**: 所有关于“温度如何交互”的规则，都写在了 `TemperatureSystem` 这一个地方, 你想知道冰、火、蒸汽、环境温度之间是怎么结算的？只需要看这一个文件，一目了然
> 2. **真正的解耦**:
>    - `火球` 不知道 `冰锥` 的存在
>    - `冰锥` 也不知道 `火焰陷阱` 的存在
>    - 它们都只知道一件事：“我负责向目标施加一个温度改变的效果”
>
> **惊人的可扩展性**:
>
> - 明天你新做一个“熔岩巨人的拳头”，它的攻击也是附加一个 `瞬时温度改变请求{数值: +400}`, 你不需要写任何新代码, 这个拳头就能**自动地**和冰锥产生蒸汽爆炸效果！因为它触发了 `TemperatureSystem` 中早已写好的`if (hasHeatRequest && hasColdRequest)` 这条规则
> - 你想加入“潮湿”状态可以部分抵消火焰？只需在 `TemperatureSystem` 中增加一条规则：`if (entity.HasComponent("Wetness")) { totalChange *= 0.5; }`, 所有火焰效果都会自动被削弱，无需逐一修改
>
> 这种设计模式让你的游戏系统像一套可以自由组合的乐高积木, 而不是一个焊死的、牵一发而动全身的电路板
