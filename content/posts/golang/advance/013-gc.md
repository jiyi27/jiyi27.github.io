## 1. 常见的垃圾回算法

- 引用计数(Reference Counting):  Python, PHP, 缺点 无法处理循环引用（A 引用 B，B 引用 A）
- 标记-清除 (Mark-Sweep): JavaScript V8, Go
- 标记-整理 / 压缩 (Mark-Compact): Java（新生代 / 老年代常用）
- 分代收集 (Generational GC): Java（HotSpot VM 默认 GC 策略之一）, .NET CLR

大致:

- Python → 引用计数 + 循环检测
- Swift / Objective-C → ARC（引用计数变种）
- PHP → 引用计数 + 循环检测
- Java → 标记-清除 / 复制 / 标记-整理 / 分代收集 / G1 / ZGC
- JavaScript (V8) → 复制（新生代） + 标记-整理（老年代） + 分代收集
- Go → 并发标记-清扫（Concurrent Mark-Sweep）
- .NET CLR → 分代收集 + 并发 GC

> Go 的垃圾回收方式是 Tracing GC，具体实现是 并发标记-清扫 (Concurrent Mark-Sweep, CMS)
>
> 核心技术是 三色标记 + 写屏障，目标是 低延迟

> Python 如何解决循环引用
>
> 1. 循环检测
>    - GC 会扫描容器对象（list, dict, class instance 等），看看是否存在“孤岛对象”
>    - 孤岛对象 = 一组对象彼此引用，但从根（全局变量、栈变量）不可达
>    - 这类对象会被识别并清理，即使它们的引用计数不为 0
>
> 2. Python 提供 `weakref` 模块，可以创建弱引用，不增加计数，从而避免循环引用问题

## 2. Go Values 存在哪 - 逃逸分析

[官方文档](https://tip.golang.org/doc/gc-guide#Where_Go_Values_Live)说的很好了, 这里稍微整理, 复制粘贴一下, 当作笔记

For instance, non-pointer Go values stored in **local variables** will likely not be managed by the Go GC at all, and Go will instead arrange for memory to be allocated that's tied to the [lexical scope](https://tip.golang.org/ref/spec#Declarations_and_scope) in which it's created. In general, this is more efficient than relying on the GC, because the Go compiler is able to predetermine when that memory may be freed and emit machine instructions that clean up. Typically, we refer to allocating memory for Go values this way as "stack allocation," because the space is stored on the **goroutine stack**.

Go values whose memory cannot be allocated this way, because the Go compiler cannot determine its lifetime, are said to ***escape to the heap*.** There are many reasons why a Go value might need to escape to the heap. One reason could be that its size is dynamically determined. Consider for instance the backing array of a slice whose initial size is determined by a variable, rather than a constant. 

> 这里就可以看出来, 对象存储的位置很容易猜到, Go 编译器不确定什么时候回收, 就会放到 Heap 上

>  只要是指针类型指向的对象，就一定放堆上吗? 值类型的本地变量就一定放 Stack 上吗
>
> 未必, 栈上分配
>
> ```go
> func f() {
>     x := 10
>     p := &x
>     fmt.Println(*p)
> }
> ```
>
> 这里 `x` 其实可以放在栈上, `p` 指针只在 `f` 的作用域内有效, 函数返回后整个栈帧销毁, `x` 也自然消失，不需要 GC
>
> 堆上分配（逃逸）
>
> 当编译器检测到“变量在函数返回后还会被用到”，比如
>
> ```go
> func f() *int {
>     x := 10
>     return &x  // x 逃逸
> }
> ```
>
> 这里 `x` 虽然不是指针类型, 但也必须放堆上，因为函数返回后调用者还要访问它
>
> 所以关键是 **逃逸分析 (escape analysis)**：
>
> - 如果编译器能证明对象只在当前栈帧内使用，就分配在栈上
> - 否则分配在堆上，由 GC 管理

## 3. 追踪式 GC

Garbage collection may refer to many different methods of automatically recycling memory; for example, reference counting. In the context of this document, garbage collection refers to **tracing** garbage collection, which identifies in-use, so-called live, objects by following pointers transitively.

这段话的大致意思是虽然垃圾回收有很多实现方式（比如引用计数），但这里的“垃圾回收”专门指 **追踪式 GC** —— 它的原理是通过不断沿着对象之间的指针关系传递，找出所有仍然存活的对象

Let's define these terms more rigorously:

- Object—An object is a dynamically allocated piece of memory that contains one or more Go values.
- Pointer—A memory address that references any value within an object. This naturally includes Go values of the form `*T`, but also includes parts of built-in Go values. Strings, slices, channels, maps, and interface values all contain memory addresses that the GC must trace.

这段话是在说, 接下来的讨论中, 对象就是动态分配的内存块, 指针就是指向该内存块的地址, 应该是为了方便解释 GC 吧, 这里可能会有一种觉得 Java, Python 的内存模型很相似了, 变量一般是 reference, 指向放在堆上的对象, Go 与他们不同的是, 并不是所有的值都放在heap, 也可能放在 function stack 上, 具体在哪, 上面的逃逸分析部分已经讨论了

Together, objects and pointers to other objects form the **object graph**. To identify live memory, the GC walks the object graph starting at the program's **roots**, pointers that identify objects that are definitely in-use by the program. Two examples of roots are local variables and global variables. The process of walking the object graph is referred to as **scanning**. Another phrase you might see in the Go documentation is whether an object is **reachable**, which just means that the object can be discovered by the scanning process. Note also that, [with one exception](https://tip.golang.org/doc/gc-guide#Finalizers_cleanups_and_weak_pointers), once memory becomes unreachable, it stays unreachable.

这段话就是在说 Go 的 GC 如何判定一个对象是否存活 —— 通过 根扫描 + 对象图遍历 来确定哪些是可达对象，剩下的就是垃圾：

1. 程序里的所有对象和它们之间的指针关系，构成了一张大图（object graph）
2. GC 从根（栈上的局部变量、全局变量）出发，一路顺着指针去找，把能找到的都标记为“活的”
3. 找不到的对象就是“不可达的”，说明程序再也没法访问它们了，可以安全回收
4. 不可达的对象不会“复活”，除非你用了 finalizer（类似 Java 的 finalize，但 Go 里很少用）

This basic algorithm is common to all tracing GCs. Where tracing GCs differ is what they do once they discover memory is live. Go's GC uses the mark-sweep technique, which means that in order to keep track of its progress, the GC also **marks** the values it encounters as live. Once tracing is complete, the GC then walks over all memory in the heap and makes all memory that is *not* marked available for allocation. This process is called **sweeping**.

One alternative technique you may be familiar with is to actually *move* the objects to a new part of memory and leave behind a forwarding pointer that is later used to update all the application's pointers. We call a GC that moves objects in this way a **moving** GC; Go has a **non-moving** GC.

大致是在说上面说的基本算法（从根开始遍历对象图，找出存活对象）是所有 Tracing GC 的共性, 不同的 Tracing GC 差别在于: 当发现对象是“活的”之后, 怎么处理

Go 的 GC 用的是 Mark-Sweep（标记-清扫）

- 标记 (Mark)：在遍历时，遇到活的对象就打上“存活”的标记
- 清扫 (Sweep)：遍历完后，再走一遍堆，把所有没有标记的内存块回收, 就是说, 告诉系统这些内存块可以用来分配给新的对象了

另一种常见做法：

- 有的 GC（比如 Java 的某些收集器、很多教材里的例子）会在发现活对象后，把它们 move) 到新的内存区域，并在原位置留一个“转发指针 (forwarding pointer)”，后续再更新程序里的所有引用
- 这种做法叫 Moving GC: 把活的对象复制到新区域，腾出一整块大内存（避免碎片化，分配快），但需要额外的拷贝成本和更新指针的工作

Go 的特点：

- Go 的 GC 是 non-moving（非移动式）：也就是说它不会搬运对象，只是标记哪些对象活着，然后清理不是活着的对象
- Go 为什么不用 Moving GC
  -  Go 强调 低延迟 (low latency)，而对象搬运会增加 STW 或并发更新的复杂度
  - Go 里有很多和 C 库交互的场景（cgo、指针传递），对象地址不能轻易变
