## 1. API 限流

常见的 API 限流方式有 令牌桶/漏桶、固定窗口/滑动窗口 等

### 1.1. 先澄清需求

- 限流对象：只针对某个接口？还是“接口 + 用户/Token/IP”？（例如：`/api/order` 每个用户 5 req/s）
- 口径：速率（RPS）还是并发数（同时在处理的请求数）？很多写操作更关心并发上限
- 反馈方式：超过限额返回 429 Too Many Requests 还是排队/降级？
- 范围：单实例限流还是分布式（多副本统一配额）？

### 1.2. 选择限流“维度键”

- 按接口限流：key = `route:/api/order`
- 接口 + 用户：key = `route:/api/order#uid:123`
- 接口 + IP：key = `route:/api/order#ip:1.2.3.4`
- 接口 + 租户：key = `route:/api/order#tenant:acme`

### 1.3. 算法选型（能清楚区别与取舍）

- 令牌桶（Token Bucket）：按速率产令牌，请求消耗令牌；允许可控突发
  - 适合大多数 API；配置简洁：rate + burst

- 漏桶（Leaky Bucket）：恒定出水速率，平滑但更“刚性”，突发被排队/丢弃
  - 更适合对下游“极稳入口”的场景

- 固定窗口（Fixed Window）：实现简单，但窗口边界有突刺问题
- 滑动窗口（Sliding Window / Log/Counter）：最公平但复杂、存储更重
- 并发限流（Semaphore）：限制“同时在处理的请求数”，常配合上面任一“速率限流”
  - 适合慢接口（如支付、导出、调用下游）

> 面试点：速率与并发是两个维度，通常组合更稳（例如：5 req/s + 并发≤20）

### 1.4. 限流的“落点”与职责边界

- 应用内中间件（Go 服务内）：延迟最小，适合单实例或本地控制；分布式需外部状态
- 边车/网关层（Nginx/Envoy/Kong/API Gateway）：对多服务统一策略与审计，适合跨实例统一配额
- 两层限流：网关做粗粒度（防 DDoS/热接口），服务内做细粒度（接口+用户）

### 1.5. 单机 vs 分布式的状态管理

- 单机（一个进程内）

  - 用内存结构维护 limiter（map/sync.Map），每个 key 一个桶；要有闲置回收（idle TTL）避免内存泄露

  - 时钟依赖小（令牌桶按请求时间推进），性能高

- 分布式（多副本共享配额）

  - 用 Redis / etcd 做集中状态：
    - 固定/滑动窗口：`INCR` + `EXPIRE`；简易但有突刺
    - 令牌桶：建议 Lua 脚本原子更新（读-改-写在 Redis 内完成），否则会竞争

  - 键设计：如 `rl:{route}:{dim}:{timebucket}` 或 `tb:{route}:{dim}`

  - 热点 & 扩散：对热接口，配额按用户维度摊开，或在键里加随机抖动（jitter）

### 1.6. 超额后的策略（不要只会 429）

- 硬拒绝：直接 429（最简单，保护后端最强）
- 软排队：短时间自旋或有限队列（保护下游，但要防“排队放大延迟”）
- 降级：返回缓存/概览/部分字段（读接口更适合）
- 回退到全局限流：接口级爆了还能落到更粗口径，避免系统雪崩

### 1.7. 边界与坑

- 时间窗口突刺：固定窗口会在边界时翻倍，必要时用滑动窗口或令牌桶
- 时钟漂移：分布式滑窗要考虑机器时钟偏差（NTP、服务端统一时间源）
- GC 与内存：大量用户维度 key 会爆内存，务必闲置回收（idle TTL，LRU）
- 热 key：热门接口/租户导致 Redis 热点，需分片或 hash tag 控制
- 幂等性：被拒绝或重试场景，写操作要有幂等键（如订单号）避免重复落库
- 链路背压：仅“入口限流”不够，必要时在下游（数据库/外部 API）也要限速或熔断

## 2. 排队怎么实现?

排队的实现通常有两种: 

- 一种是应用内用有界队列 + worker 池, 超过并发上限的请求进入队列排队执行，如果队列满就直接拒绝；
- 另一种是基于令牌桶的阻塞式 `Wait`，没令牌的请求就会等待直至可执行, 对于耗时较长的操作，还可以把请求丢进 Kafka/SQS 等消息队列，后端按速率消费

关键点是队列一定要有上限，并设置等待超时，否则可能导致雪崩或长时间卡死

- 队列必须有上限（否则可能堆满内存/消息堆积 → 雪崩）
- 等待时间要可控（超时丢弃/返回错误，否则用户体验差）
- 队列模式适合非实时接口（如报表导出、批处理），但不适合支付/下单这种强实时写操作
- 限流 + 排队要结合使用：一般前面网关先做限流（避免洪水），内部对慢接口再做排队

### 2.1. 有界队列 + worker 池

如果请求到达速度大于处理能力, 仅靠限流丢弃并不优雅, 于是引入了

有界队列 (Bounded Queue)

- 请求先进来排队
- 队列满了 → 立即拒绝请求，避免系统崩溃

Worker 池 (Worker Pool)

- 用固定数量的 worker goroutine 从队列里取任务执行
- 避免无限开 goroutine 把内存打爆

队列充当 缓冲区, Worker 池保证 最大并发度, 系统在超载时 快速拒绝，而不是积压请求

### 2.2. 单结口限流

请求进来 → 转成 `EmailTask` → 入队 → worker 处理

HTTP Handler：

```go
http.HandleFunc("/sendEmail", func(w http.ResponseWriter, r *http.Request) {
    to := r.FormValue("to")
    subject := r.FormValue("subject")
    body := r.FormValue("body")

        w.Write([]byte("Email queued\n"))

    }

type EmailTask struct {
    To      string
    Subject string
    Body    string
}
```

worker：

### 2.3. 整体 API 限流

全局 API 限流常用「令牌桶 / 漏桶」算法，放在中间件里统一实现最合适

Go 的 HTTP 中间件一般是一个函数，接收 `http.Handler`，返回一个新的 `http.Handler`，比如

```go
func rateLimitMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // 限流逻辑
        if !allowRequest() {
            http.Error(w, "Too Many Requests", http.StatusTooManyRequests)
            return
        }

        next.ServeHTTP(w, r) // 继续执行后续 handler
    })
}
```

限流逻辑怎么写？固定窗口计数

```go
var mu sync.Mutex
var count int
var windowStart = time.Now()

const limit = 100 // 每秒最多 100 个请求

func allowRequest() bool {
    mu.Lock()
    defer mu.Unlock()

    now := time.Now()
    if now.Sub(windowStart) > time.Second {
        // 进入新的一秒，重置计数
        count = 0
        windowStart = now
    }

    if count < limit {
        count++
        return true
    }
    return false
}
```

 令牌桶（更平滑）

```go
var tokens = make(chan struct{}, 100) // 桶容量 100

func init() {
    // 每 10ms 往桶里放一个 token
    go func() {
        ticker := time.NewTicker(10 * time.Millisecond)
        for range ticker.C {
            select {
            case tokens <- struct{}{}:
            default: // 桶满了就丢弃
            }
        }
    }()
}

func allowRequest() bool {
    select {
    case <-tokens: // 取到 token，允许
        return true
    default:
        return false
    }
}
```

> ```go
> for range ticker.C {
>     select {
>     case tokens <- struct{}{}:
>     default: // 桶满了就丢弃
>     }
> }
> ```
>
> `select` 的意思是 **尝试执行一组 channel 操作**
>
> `case tokens <- struct{}{}` 
>
> - 表示尝试往 `tokens` 这个 channel 里放一个空结构体（相当于加一个 token）
> - 如果 `tokens` 还没满，就成功放进去，case 执行
> - 如果 `tokens` 已经满了，这个分支就会阻塞, 尝试其它分支
>
> `default`:
>
> - `select` 里有 `default`，表示这个 `select` 是非阻塞模式
> - 如果上面的 `case` 不能立即执行（即 channel 满了），就直接走 `default` 分支
>
> 为什么不直接写成下面这样
>
> ```go
> for range ticker.C {
>     tokens <- struct{}{} // 往桶里放 token
> }
> ```
>
> 当桶满了时，`tokens <- struct{}{}` 会 阻塞, 阻塞写法也确实是“每个 tick 产出一个 token”，但它会在桶满时卡住，从而把节奏「拖慢」到和消费速率一致，不再是“恒定速率”

> 因为实际业务里，单纯全局限流往往不够
>  想象一下：
>
> - 全局限流设置 5000 QPS
> - 结果某个大客户单独打了 5000 QPS，把全局额度吃完 → 其他人全被拒绝
>
> 所以实际生产里，常见做法是：
>
> - 先做 全局限流（保护整体服务）
> - 再做 per-user / per-IP 限流（防止个别用户滥用）

## 3. 分布式限流

单机内用 channel/worker 就够；分布式要把“状态”放到所有实例都能看到的地方

### 3.1. **边缘/网关层限流** 

NGINX `limit_req` / `limit_conn`：简单、稳定，但节点本地计数，多台 NGINX 时就不是全局一致的

云网关（API Gateway/Cloudflare/WAF）：“托管+全局”，最省心，但可定制度受限、计费

### 3.2. 应用侧 + Redis/Lua 原子脚本

这是一个使用 Redis 实现的，基于令牌桶 (Token Bucket) 算法的速率限制 (Rate Limiting) 脚本

它的主要作用是控制某个操作或API的请求频率, 例如，你可以用它来限制一个用户每秒最多只能调用某个接口5次。如果请求过于频繁，脚本会拒绝请求，并建议客户端需要等待多久后才能重试

- 令牌桶 (Token Bucket)：有一个固定容量（`capacity`）的桶，里面装着令牌（`tokens`）
- 令牌生成 (Token Refill)：系统会以一个固定的速率（`rate`）向桶里添加新的令牌
- 当一个请求到来时，它需要从桶里获取一个或多个令牌（`cost`）
  - 如果桶里的令牌足够，请求被允许，并消耗掉相应数量的令牌
  - 如果桶里的令牌不够，请求被拒绝

> 下面的脚本只用了 Redis 的 `String` 数据类型
>
>  针对这个 `String` 数据结构，脚本只用了两个最基础的操作
>
> - 使用 `GET key` 读取整个字符串, **在脚本中**: `redis.call('GET', key)` 这行代码执行后，会得到类似 `"42.75:1756359261000"` 这样的一个**完整字符串**，并存入 Lua 的 `data` 变量中, Redis 本身并不知道这个字符串里有冒号，它只把它当成一整块数据
> - `SET key value [PX milliseconds]`
>   - 作用: 写入（或覆盖）整个字符串，并设置一个以毫秒为单位的过期时间
>   - 在脚本中: `redis.call('SET', key, new_value, 'PX', ttl_ms)` 这行代码会把计算出的新状态（例如 `"41.75:1756359261500"`）作为一整个字符串，完全覆盖掉 Redis 中旧的值
>
> Key 的设计与值的解析
>
> - 脚本里的 `KEYS[1]` 只是一个参数占位符, 可以把它理解为函数的一个参数
>
> - ```lua
>   -- 就像一个函数定义
>   function rate_limiter(key, capacity, rate, now_ms, cost)
>     -- ... 脚本逻辑 ...
>   end
>   ```
>
> - 在调用这个脚本时，需要从你的应用程序代码（比如 Java, Python, Go）中传入一个具体的 `key`, 这个 `key` 是由你根据业务逻辑来动态生成的
>
>   - 如果你想限制用户 `user123`，你就传入 `rate_limit:user:123`
>   - 如果你想限制 IP `1.2.3.4`，你就传入 `rate_limit:ip:1.2.3.4`
>
> - 所以，Key 的设计是完全灵活的，由调用方决定，脚本只负责对传入的那个 `key` 进行操作

> 为什么要使用 lua 脚本 有哪些考量?
>
> 在 Redis 中使用 Lua 脚本主要是为了保证原子性和提升性能, Redis 在执行一个 Lua 脚本时，会把整个脚本作为一个独立的、不可分割的命令来执行, 在脚本运行期间，Redis 不会处理任何其他客户端发来的命令
>
> 原子性:
>
> 类似库存扣减, 先检查后扣减, 可能因为客户端同时查询额度, 然后因为网络延迟, 都成功判断为可以通过请求, 比如服务器先发送一个 GET 请求判断令牌余额, 发现 A 请求可以通过, 此时服务器接着要发送 SET 请求, 让余额减一, 在这中间, B 请求来到, 服务器的其他线程又发送了 GET 请求, 发现余额充足, 可以接受, 可是实际并不充足了, 只是服务器的那个 SET 请求还没发送到 Redis 服务器
>
> 性能:
>
> 没有脚本: 客户端需要和 Redis 进行多次网络通信（一次 `GET`，一次 `SET`）, 一来一回的网络延迟（RTT, Round-Trip Time）会累加
>
> ```
> 客户端 <--- RTT ---> Redis (GET)`
> 客户端 <--- RTT ---> Redis (SET)
> ```
>
> 使用脚本: 客户端只需要发送一次脚本到 Redis，然后等待一次结果返回即可。所有中间计算都在 Redis 服务器端完成
>
> ```
> 客户端 <--- RTT ---> Redis (EVAL)
> ```

```lua
-- KEYS[1] = rate_limit key
-- ARGV[1] = capacity
-- ARGV[2] = rate (tokens per second)
-- ARGV[3] = now_ms (use Redis TIME 而非本地时钟也可)
-- ARGV[4] = cost (default 1)
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now_ms = tonumber(ARGV[3])
local cost = tonumber(ARGV[4])

local data = redis.call('GET', key)
local tokens, last_ms

if data then
  local sep = string.find(data, ':')
  tokens = tonumber(string.sub(data, 1, sep-1))
  last_ms = tonumber(string.sub(data, sep+1))
else
  tokens = capacity
  last_ms = now_ms
end

-- 补充令牌
local delta = math.max(0, now_ms - last_ms)
local refill = delta * rate / 1000.0
tokens = math.min(capacity, tokens + refill)
last_ms = now_ms

local allowed = 0
local remaining = tokens
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
  remaining = tokens
end

-- 写回，并设置闲置自动过期（容量/速率=完全回满需要的毫秒*2）
local ttl_ms = math.floor((capacity / rate) * 1000) * 2
redis.call('SET', key, tostring(tokens) .. ':' .. tostring(last_ms), 'PX', ttl_ms)

-- 返回：是否允许，剩余可用令牌（向下取整），建议等待毫秒
local wait_ms = 0
if allowed == 0 then
  wait_ms = math.ceil((cost - tokens) * 1000 / rate)
end

return { allowed, math.floor(remaining), wait_ms }
```

```go
import (
	"context"
	"time"

	"github.com/redis/go-redis/v9"
)

var rdb = redis.NewClient(&redis.Options{Addr: "127.0.0.1:6379"})

// 把上面的 Lua 脚本放到 limiterLua 变量
func Allow(ctx context.Context, key string, capacity int, rate float64, cost int) (allowed bool, remaining int, retryAfter time.Duration, err error) {
	nowMs := time.Now().UnixMilli()
	res, err := rdb.Eval(ctx, limiterLua, []string{"rate_limit:" + key},
		capacity, rate, nowMs, cost).Result()
	if err != nil {
		return false, 0, 0, err
	}
	arr := res.([]interface{})
	allowed = arr[0].(int64) == 1
	remaining = int(arr[1].(int64))
	retryAfter = time.Duration(arr[2].(int64)) * time.Millisecond
	return
}

// 中间件里使用
// 例：全局每秒 1000 次，突发 2000
func rateLimitMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		key := "global" // 也可以按租户/IP/路径组合: tenant:ip:/api/foo
		ok, _, retryAfter, err := Allow(r.Context(), key, 2000, 1000, 1)
		if err != nil {
			// Redis 故障的降级策略：fail-open 或 fail-close
			http.Error(w, "rate limit error", 503)
			return
		}
		if !ok {
			w.Header().Set("Retry-After", strconv.Itoa(int(retryAfter.Seconds())+1))
			http.Error(w, "Too Many Requests", 429)
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

上面的脚本只用了 Redis 的 `String` 数据类型, 你可能会觉得奇怪，因为它需要存储两个值（`令牌数` 和 `时间戳`），为什么不用 `Hash` 这样的结构呢？

原因如下：

- **性能和原子性**: 将两个值合并在一个字符串里，只需要一次 `GET` 读取和一次 `SET` 写入, 如果使用 `Hash`，也可以，对于这种极高频的操作，使用简单的 `String` 结构, 性能是最优的, 当然也可以用哈希, 差别不算太大, 就是设置过期时间
- **简洁性**: 脚本的逻辑就是读取整个状态，在内存中计算，再把整个新状态写回去, `String` 完美地满足了这个需求

> 使用 String 的操作流程:
>
> 数据存储的样子:
>
> - Key: `rate_limit:user:123`
> - Value: `"58.4:1756359261000"` (一个单独的字符串)
>
> 操作流程:
>
> 1. `GET rate_limit:user:123` -> 得到一个字符串
> 2. Lua 内部: 对这个字符串进行分割、解析
> 3. `SET rate_limit:user:123 "57.4:1756359261500" PX 30000` -> 将新状态作为一个完整的字符串写回去，并同时设置过期时间
>
> 如果使用 `Hash` 方式
>
> 数据存储的样子:
>
> - Key: `rate_limit:user:123`
> - Value: (一个 Hash 结构)
>   - Field `tokens` -> Value `"58.4"`
>   - Field `last_ms` -> Value `"1756359261000"`
>
> 读取数据
>
> - String 方式: `redis.call('GET', key)`
> - Hash 方式: 你需要用 `Hash` 的命令来读取
>
> ```lua
> -- 返回一个列表, 例如 {"58.4", "1756359261000"}
> local data = redis.call('HMGET', key, 'tokens', 'last_ms') 
> -- 解析逻辑也变了，不再是分割字符串，而是从列表取值
> local tokens = tonumber(data[1])
> local last_ms = tonumber(data[2])
> ```
>
> 写入数据
>
> - String 方式: `redis.call('SET', key, new_value, 'PX', ttl)`
>
> - Hash 方式: 你需要用 `Hash` 的命令来写入
>
> ```lua
> -- 同时设置 tokens 和 last_ms 两个字段的值
> redis.call('HMSET', key, 'tokens', new_tokens, 'last_ms', new_last_ms)
> ```
>
> 设置过期时间
>
> - String 方式: `SET` 可以原子性地完成“写入数据”和“设置过期时间”这两件事, 这是一个单一的操作
> - Hash 方式: `HMSET` 命令不能在设置字段的同时设置整个 `key` 的过期时间, 必须分两步走
>   - 用 `HMSET` 更新数据
>   - 再用 `PEXPIRE` 或 `EXPIRE` 命令为这个 `key` 设置过期时间
>
> ```lua
> redis.call('HMSET', key, 'tokens', new_tokens, 'last_ms', new_last_ms)
> redis.call('PEXPIRE', key, ttl_ms)
> ```
